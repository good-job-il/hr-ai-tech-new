# Правила работы с проектом HeadHunter / hr-ai.tech

Эти инструкции обязательны во всех чатах и задачах, работающих с этим репозиторием. В начале каждого чата читать этот файл и применимые вложенные `AGENTS.md`. Не полагаться на память предыдущих чатов.

## Документация — источник требований проекта

- Перед анализом, ответом по проекту и изменениями читать `docs/project-overview.ru.md`, соответствующие разделы `docs/project-documentation.pdf` и относящиеся к задаче актуальные документы проекта в Linear. Проверять также новые документы в `docs/` после синхронизации GitHub.
- Опираться только на документированные требования и явные указания пользователя. Не придумывать бизнес-правила, функции, интеграции, статусы готовности и архитектурные решения по аналогии с другими продуктами или по памяти модели.
- Код, миграции, тесты и проверки среды использовать для сверки фактической реализации, а не как разрешение расширять требования. Технические руководства установленных зависимостей использовать для корректного исполнения документированных требований.
- Учитывать дату и область каждого источника. PDF и обзор содержат исторические снимки; `README.md` и `REPORT.txt` содержат устаревшие сведения и не заменяют актуальную спецификацию. Старые пути, количества записей и результаты проверок не считать текущими фактами.
- При расхождении документов, задачи Linear и реализации явно фиксировать расхождение. Если оно влияет на требуемое поведение и не разрешается актуальными документами или указаниями пользователя, уточнить решение до изменения соответствующего поведения.
- При изменении поведения обновлять затронутую документацию проекта вместе с кодом. Не выдавать наличие кода или локального теста за подтверждение работы облака.

## GitHub: синхронизация, изменения и публикация

- Репозиторий: `git@github.com:good-job-il/hr-ai-tech-new.git`; основная ветка: `main`.
- Перед началом написания кода в каждой задаче проверить `git status`, текущую ветку и remote, затем выполнить `git pull origin main`. При обновлении существующей задачи повторять синхронизацию перед новым этапом правок, если удалённая ветка могла измениться.
- Не начинать правки кода, если pull не выполнен успешно. Не обходить конфликт удалением чужих изменений, `reset --hard`, `clean` или принудительным push. Сначала безопасно разрешить конфликт; при неоднозначном выборе сохранить работу и запросить решение пользователя.
- Сохранять незакоммиченные изменения пользователя и других чатов. Не включать их в свой коммит. При необходимости работать в отдельном worktree или ветке `codex/...`, синхронизированной с `origin/main`, не переключая занятую чужой работой ветку.
- После синхронизации самостоятельно выполнить необходимые изменения и подходящие проверки. Проверить diff; включать в коммит только файлы своей задачи, без секретов, персональных данных и служебных артефактов.
- После успешных проверок самостоятельно создать коммит и выполнить обычный `git push` в соответствующую ветку `origin`. Для задачи в `main` — `git push origin main`; для отдельной ветки — `git push -u origin <ветка>`. Не считать push отдельной ветки слиянием в `main`.
- Пользователь разрешил обычные pull, коммиты и push в рамках порученной задачи без повторного запроса подтверждения. Это не разрешение на force push, обход защиты веток или несвязанные изменения. Если защита ветки требует PR, следовать этому процессу.
- Проверить успешность push и сообщить ветку, SHA, результаты проверок и оставшиеся ограничения. При ошибке синхронизации или публикации явно сообщить о ней, сохранив выполненную работу.

## Linear: обязательная синхронизация хода работы

- Использовать подключённый плагин Linear. Рабочее пространство: `hr-ai-tech`, команда: `Hr-ai-tech`; известный проект: «HeadHunter — Спринт 01: готовность к пилоту» (`c74ae8ff-c5d7-4b6d-857f-ed08c811de79`). Для другой задачи проверять её принадлежность и актуальный проект, не назначать этот спринт автоматически.
- В начале каждой задачи прочитать связанную задачу Linear: описание, критерии готовности, текущий статус, комментарии, зависимости и документы. Если идентификатор не дан, найти подходящую задачу по содержанию; при отсутствии создать задачу в подходящем проекте команды без дублирования существующей.
- Перед правками согласовать объём работы с задачей и документацией. Обновить статус на фактический этап работы, используя существующие статусы команды.
- При существенном прогрессе, изменении объёма, найденном дефекте или блокере записывать это в связанную задачу. Перед финальным обновлением перечитать её, чтобы сохранить изменения других участников. Не перезаписывать описание целиком без необходимости.
- После выполнения записать результат, проверки и ограничения, ветку, SHA и ссылку на коммит или PR. Закрывать задачу только при выполнении всех её критериев; частичную работу фиксировать без закрытия всей задачи.
- Пользователь разрешил создавать и обновлять относящиеся к порученной работе задачи, комментарии и статусы Linear без повторного запроса. Не менять несвязанные задачи.
- Поддерживать эту синхронизацию в каждом рабочем чате: начало → существенные события → завершение. Правило не запускает непрерывный фоновый процесс и не гарантирует доступность подключения. Если Linear недоступен, явно сообщить, сохранить несинхронизированный итог локально без секретов и перенести его в Linear при восстановлении доступа; не утверждать, что синхронизация состоялась.

## Иврит без niqqud

- По прямому указанию владельца от 08.11.2026 весь отображаемый текст на иврите — без niqqud и знаков кантилляции, включая импортированные вакансии, переводы, заголовки вкладок, подписи и текст sharing. Не добавлять их в новый UI-контент.
- Использовать общий слой `lib/hebrew-text.mjs`; не удалять буквы, ивритскую пунктуацию или диакритику других языков. Не переписывать рабочие записи, оригинальные файлы, секреты, URL и идентификаторы ради изменения отображения.
- При новых источниках контента проверять их путь до отображения. Запускать `tests/hebrew-text.test.mjs`; документация: `docs/public-content-seo-2026-11-08.ru.md`.

## Направление иллюстрации главной

- Цифровая голова всегда смотрит на карточку кандидата: RTL — влево, LTR — вправо. Управлять через direction, logical layout и `:dir()`, а не отдельные проверки Hebrew/English. При добавлении языка правило должно работать с его направлением.
- Карточку, текст и логотип не отражать. Решение и сохранённые функции: `docs/landing-combined-2026-11-09.ru.md`.
