| Сценарий | Фактический результат до исправления |
|---|---|
| Рекрутер без cv.download: RPC и прямое скачивание | DENIED |
| Клиент до revoke: authenticated URL | 200, CDN MISS |
| После revoke: RPC и новый URL с nonce | DENIED |
| После revoke: тот же URL | **200, CDN HIT**, private max-age около 3588 |
| После revoke: ранее выданный signed URL | **200** |
| Новый файл с cacheControl=0, тот же URL после revoke | **200, CDN HIT** |

Это воспроизводимый ответ CDN, а не предположение о локальном браузерном кэше. Простого cacheControl=0, свежего nonce или отказа RLS недостаточно для отзыва всех ранее выданных ссылок. Артефакты без токенов: `output/cv-cloud-baseline.json`, `output/cv-cloud-zero.json`. Приватный fixture manifest исключён из Git правилом `.env*`.

## Подготовленное изменение

- `/api/cv`: POST с настоящим пользовательским Bearer JWT. Организационный документ проверяется через `candidate_document_download`; клиентский — через `client_presentation_document`; файл соискателя — через новый `candidate_cv_download`. Пользовательский JWT, не secret key, определяет право доступа.
- Только после успешного RPC отдельный серверный Storage client читает байты. Ответы и ошибки имеют no-store для браузера и CDN. Ключ, Storage URL и подписанный token клиенту не выдаются. Нет публичного fallback при отказе.
- 061 вводит restrictive SELECT policy для обоих CV buckets: пользовательским JWT разрешено только перечисление метаданных по существующим RLS, получение байтов, signing, batch signing, S3/copy запрещены. Server-only secret клиент не заменяет проверку пользовательских прав.
- Все четыре пути открытия CV — карточка фонда, клиентский портал, собственный профиль, отклик/интервью — используют новый endpoint. Предпросмотр организационного PDF тоже требует cv.download: уже полученные браузером байты можно сохранить.
- Временный blob URL освобождается при закрытии/смене документа. Повторное открытие снова проходит серверную проверку. Ранее просмотренную/скачанную человеком копию физически отозвать невозможно; это не обещается.
- Права на историю, исходные карточки и общие правила сотрудничества этим этапом не расширяются.

## Обязательная конфигурация и порядок выпуска

В `.env` сейчас отсутствует `SUPABASE_SECRET_KEY`. Такой же **server-only** ключ нужен в Vercel. Не использовать NEXT_PUBLIC_, не коммитить и не отправлять ключ в переписку. Без него endpoint закрыт с 503. Не применять 061 до готовности серверной конфигурации: текущий UI ещё использует Storage напрямую.

После настройки ключа:

1. Завершить синтетический fixture второго bucket и отклика. Сохранить ранее открытый authenticated URL и signed URL только в приватном manifest.
2. Сделать контролируемую смену старых путей CV средствами Storage API с проверкой сохранности байтов и обновлением candidate_documents.object_path; ID документов/снимки и историю сохранить. Для candidate-cvs сохранить папку владельца. Не удалять единственную копию и не редактировать storage.objects вручную. Нужен журнал точных старых/новых путей вне Git и возможность безопасного восстановления при сбое.
3. Очистить CDN обоих CV buckets через официальный purge API. Переименование исключает доступ по старым signed URLs, очистка убирает старые CDN-копии. Один purge сам по себе не отзывает ещё действующий signed token.
4. Применить и повторно прочитать 061. Запустить локальную production-сборку с настоящим Supabase и выполнить `scripts/verify-cv-access.mjs <private-manifest> <base-url> <report>`; окружение передать безопасно. Runner использует настоящие пользовательские JWT и проверяет положительные/отрицательные сценарии, grant/revoke, представителя, оба buckets, запрет signing/direct download и **точные прежние URL**. Отсутствующий fixture или 503 — FAIL, а не успешный запрет.
5. Пройти браузерную приёмку реального PDF и закрытия/повторного открытия, включая телефон/iPad. Только после полного PASS разрешены push основной ветки и публикация. После публикации повторить приёмку на www и записать фактическую версию.

Чистка CDN требует secret key и доступна на Pro и выше; распространение очистки может занять до 60 секунд. Если план/ключ не позволяют очистку, публикация остаётся заблокированной, а не объявляется успешной.
